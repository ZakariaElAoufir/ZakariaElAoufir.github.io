Stack

Microservices

  • Java 21 7 services
  • Spring Boot REST, Actuator
  • Spring Cloud Gateway point d’entrée :9000
  • Spring Data JPA Flyway pour le schéma
  • Spring AI client Ollama

Données et messagerie

  • MySQL utilisateurs, appareils, alertes
  • InfluxDB 2 séries temporelles
  • Apache Kafka KRaft, energy-usage, energy-alerts
  • Kafka UI topics et messages

Sécurité et résilience

  • Keycloak JWT, het-security-realm
  • OAuth2 Resource Server validation à la gateway
  • Resilience4j circuit breaker, route de secours

Observabilité et outils

  • Prometheus /actuator/prometheus
  • Grafana tableau de bord provisionné
  • Springdoc OpenAPI Swagger UI
  • Mailpit boîte mail de test
  • Docker Compose 9 conteneurs
  • Ollama LLM local

Choix techniques

Kafka entre ingestion et usage

Pourquoi
La réception des relevés ne dépend plus du stockage : si usage-service ralentit, les messages attendent dans le topic.
Alternative
Des appels REST directs d'ingestion vers usage.
Compromis
Un broker de plus à faire tourner, et des événements à versionner des deux côtés.

InfluxDB pour les relevés

Pourquoi
Base de séries temporelles : écritures massives et sommes par fenêtre de temps (Flux) sans index à gérer.
Alternative
Une table MySQL de relevés.
Compromis
Deux bases à maintenir ; le langage Flux est spécifique.

Gateway + Keycloak

Pourquoi
Un seul point d'entrée sécurisé par JWT ; les services restent simples, derrière. Circuit breaker par route.
Alternative
Valider le jeton dans chaque service.
Compromis
La gateway devient un point critique ; le realm Keycloak se configure à la main.

IA locale avec Spring AI

Pourquoi
Les conseils sont générés sans envoyer les données de consommation à un service externe.
Alternative
Une API hébergée (OpenAI, Mistral).
Compromis
Qualité limitée par le modèle local choisi.

Prometheus + Grafana

Pourquoi
Chaque service expose ses métriques ; le tableau de bord est provisionné au démarrage, sans clic.
Alternative
Les seuls logs des services.
Compromis
Deux conteneurs de plus en local.

Limites et suites

Limites connues

  • Tant que le seuil est dépassé, une alerte repart toutes les 10 secondes : pas de déduplication.
  • L'agrégation appelle device-service puis user-service pour chaque appareil (beaucoup d'appels REST).
  • Le simulateur tire des identifiants d'appareils au hasard, y compris inexistants.
  • Jeton InfluxDB et mots de passe écrits dans la configuration.
  • Swagger agrégé : seule la documentation de user-service est branchée à la gateway.

Pistes

  • Mémoriser la dernière alerte envoyée par utilisateur.
  • Mettre en cache les propriétaires d'appareils et les seuils.
  • Secrets en variables d'environnement, realm Keycloak exporté.
  • Une interface web pour les utilisateurs.
